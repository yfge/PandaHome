# Defer application initialization during imports

## Summary

Fresh-database P2P migration validation exposed an existing application import
side effect: importing settings or models imported the FastAPI app and called
`Base.metadata.create_all` before Alembic could create its tables.

## Changes

- `api/src/app/__init__.py`: resolve the public `app` attribute lazily, preserving
  `from src.app import app` while keeping submodule imports free of web startup.
- `api/tests/test_app_import.py`: import settings and existing models in a fresh
  subprocess and assert that no SQLite database is created.

## Outcome

Alembic can load settings and metadata without pre-creating migration tables.
This prerequisite is isolated from P2P, Access and gateway feature changes.

## Verification

- `python -m pytest -q api/tests/test_app_import.py`: passed in the isolated commit checkout.
- The isolated P2P migration upgrade/downgrade/upgrade now passes; the initial
  pre-fix check failed with `table users already exists`.
- Full backend tests and pre-commit gates are being rechecked after concurrent
  integration changes; final results are recorded before commit.

## Next steps

Retain the existing explicit `src.app.main:app` server entry point. Proceed with
the feature migrations and preserve other chats' changes in shared files.
